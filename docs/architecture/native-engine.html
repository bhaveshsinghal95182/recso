How the native engine fits into recso

recso records the screen, lets you edit zooms, cuts, cursor and webcam, and exports an MP4. On this branch every heavy pixel operation (capture, decode, compositing, encode) runs in velocity, a Rust addon, on the GPU. JavaScript only describes what to draw.

Design rules the code depends on

Layout is resolved in JS

The webcam anchor grid, canvas padding and scale all become pixel rects before the engine sees them. One placement formula in the app instead of two that have to agree.

Everything is a quad

The video is placed into a rect rather than being the frame. That's what makes room for a background and borders, and zoom is just scaling rects about a pivot.

One clock, two decoders

The camera is a second decoder pulled to the screen frame's timestamp. Screen capture can run at 1.7 fps on an idle desktop against a 30 fps camera, so the last camera frame is held.

Re-grading doesn't re-decode

Each pool slot keeps the NV12 it came from. A slider change re-runs two shader passes over pixels already on the GPU, instead of a 300–600 ms seek per event.

Same GPU or black preview

A shared handle only means something on the adapter that made it. The engine and Chromium both ask for the high-performance GPU, and checkGpuMatch() logs both at startup.

Sandbox off, isolation on

A sandboxed preload has no sharedTexture, so the editor window runs unsandboxed. Context isolation stays on and Node integration stays off.

Not there yet

  • Audio isn't the master clock. Preview plays an audio element synced to the video clock, not the other way round.
  • Windows only. Everything under velocity/src/engine/ is #[cfg(windows)].
  • H.264 only. Older HEVC recordings need the paid Store extension to open in the engine.
  • One clip per project. Neither the engine nor the old compositor has multiple clips.
  • BT.709 studio swing assumed. No BT.601, full range or HDR.
